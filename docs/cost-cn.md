# 开销

[English](cost.md) · **简体中文**

控制一把风扇需要多少开销，数据在 TYAN S8030GM2NE 上测得（AST2500、ipmitool 1.8.19、
Debian 13，2026-10-25）。所有数字都来自该机器。

相关：[设计](design-cn.md) · [配置](config-cn.md) · [平台](platform-cn.md)

## 一个周期的总开销

| 步骤 | 耗时 | 说明 |
| --- | --- | --- |
| 读取分区用到的全部传感器（4 个温度 + 3 个转速） | 183 ms | 一次 `ipmitool exec` |
| 显卡，进程内首次调用 | 31 ms | `dlopen` NVIDIA 库 |
| 显卡，此后每次 | < 1 ms | 每设备 5 µs |
| 聚合、查曲线、合并 | 微秒级 | 少量数值的算术运算 |
| 写入变化的引脚（4 个） | 135 ms | 一次 `ipmitool exec`，仅在值变化时 |
| **稳态合计** | **每 10 秒周期约 185 ms** | 单核的 1.8 %，常驻 28 MB |

连续运行 7 小时 36 分后累计 CPU 时间 **5.5 秒**，为单核的 0.02 %。空载时进程在周期之间
休眠，不产生任何写入。

## 读取

`ipmitool sdr` 遍历整张传感器表，逐行发出 Get Sensor Reading：53 行、53 次往返、每次
**2.9 秒**，与需要几个值无关。

| 方式 | 1 个读数 | 4 个 | 7 个 |
| --- | --- | --- | --- |
| `ipmitool sdr`（整表，53 行） | 2 925 ms | 2 925 ms | 2 925 ms |
| `ipmitool sdr get <name>`，每个名字一个进程 | 156 ms | — | — |
| **`ipmitool exec` + raw**（fanctl 采用） | **88 ms** | **130 ms** | **183 ms** |

各取五次中的最快值，测量时控制循环已停止，没有其他进程访问 BMC。

开销的单位是进程而不是传感器。`ipmitool` 启动、读 `/dev/ipmi0`、打开接口约需 75 ms；
同一进程内每多一条 `raw 0x04 0x2d` 增加 13–17 ms。一个进程读七个值比两个进程各读一个
更便宜。

`sdr get` 同样不具扩展性：每个名字都是一次进程启动加一次整表遍历，单个传感器 156 ms，
同一次测量中三个传感器 2.6 秒。BMC 应答慢的传感器会拖慢同一次调用中的所有读数。因此
守护进程的热路径不使用它；`check` 只用它一次，用于核对编号。

`exec` 从 stdin 读取命令列表：

```text
raw 0x06 0x01                                   # 分隔符，15 字节
raw 0x04 0x2d 0x01                              # CPU_Tctl
raw 0x06 0x01
raw 0x04 0x2d 0x60                              # CPU_FAN 转速
```

每条命令前插入分隔符，使得失败的命令留下一个空槽位，而不是让后续读数错位到别的名字上，
见[设计](design-cn.md#读取)。分隔符本身的开销无法测出：带分隔符读七个值（183 ms）与不
带分隔符读四个值（130 ms）的单条增量相同。

## 写入

同一机制：

| 方式 | 4 个引脚 |
| --- | --- |
| `ipmitool raw` 逐个引脚，四个进程 | 419 ms |
| **一次 `ipmitool exec`** | **135 ms** |

各为单次测量；同一机器此前的测量结果为 356 ms 与 125 ms。BMC 延迟有数十毫秒的波动，
因此这组数据应理解为"约 3 倍"，而不是精确值。

只写入确认值发生变化的引脚，因此温度稳定的机器不产生任何写入：十分钟的实控中，第一轮
写入四条命令，之后为零。

每条命令是否成功由 BMC 的应答（`fd 19 00`，三个字节）逐个判定，而不是看 `ipmitool` 的
退出码。`exec` 遇到失败命令会继续执行，但整体仍返回 1，退出码无法指出是哪个引脚失败；
槽位协议按引脚给出答案。

## 二进制体积

1 505 464 字节（1.44 MiB），已 strip，`lto = "thin"`、`codegen-units = 1`、
`panic = "abort"`。除 libc 和 libgcc_s 外静态链接。

| 分区 | 字节 | 占文件 |
| --- | --- | --- |
| `.text`（代码） | 1 200 774 | **79.8 %** |
| `.rodata`（常量、字符串、表） | 90 630 | 6.0 % |
| `.eh_frame` + `.eh_frame_hdr`（栈展开表） | 99 352 | 6.6 % |
| `.rela.dyn`（动态重定位） | 57 456 | 3.8 % |
| `.gcc_except_table` | 5 860 | 0.4 % |
| 文件头、节头、对齐 | ~51 400 | ~3.4 % |

### 代码来源

把每个 `.text` 符号按定义它的 crate 归类（demangle 后共归到 1 194 564 字节）：

| Crate | 占代码 | 是什么 |
| --- | --- | --- |
| `fanctl` | **17.9 %** | 本程序，约 5 200 行 |
| `clap_builder` | 17.9 % | 命令行解析 |
| `core` | 14.2 % | `Option`、迭代器、格式化 |
| `std` | 9.5 % | 标准库 |
| `toml_edit` | 8.2 % | TOML 解析（经 `toml`） |
| `alloc` | 6.5 % | 内存分配 |
| `gimli`、`addr2line`、`rustc_demangle` | 5.7 % | panic backtrace 的符号化 |
| `nvml_wrapper_sys` | 4.6 % | NVIDIA 驱动绑定 |
| 无法归因 | 2.8 % | 符号名里没有 crate 的胶水 |
| `winnow` | 2.1 % | 解析器组合子，在 `toml` 下面 |
| `tracing_subscriber` | 1.9 % | 日志管道 |
| `hashbrown` | 1.5 % | `HashMap` |
| 约 45 个更小的 crate | 7.2 % | `signal-hook`、`miniz_oxide`、`strsim`…… |

命令行解析与守护进程本身相当：两个子命令、四个参数，`clap` 占 18 % 的代码。彩色输出已
关闭（`default-features = false`），省下 81 KB；其余是 derive 机制与帮助信息渲染器。
手写 `argv` 的 `match` 可以去掉大部分，代价是失去自动生成的 `--help`。

`panic = "abort"` 在本代码库上使文件减小 29 %，因为它去掉了所有 landing pad 与大部分
`.eh_frame`。栈展开表仍占 6.6 %，因为 `std` 的 `catch_unwind` 需要它。代价是 panic 没有
符号化调用栈；需要调用栈时用 `--config 'profile.release.panic="unwind"'` 重新编译。

TOML 及其解析器组合子约占 10 %。配置每个进程只读一次，这部分开销换来的是便利。

可选特性的体积可以测出：`--no-default-features`（不含 NVML，无显卡温度）编译结果为
**1 399 248 字节**，小 106 KB。

## 运行时占用

| 编译配置 | RSS | 匿名内存 | 线程 |
| --- | --- | --- | --- |
| 默认（含 NVML） | 28 MB | 21 MB | 2 |
| `--no-default-features` | 8 MB | 1.2 MB | 1 |

差异来自链接 NVIDIA 库，驱动把自己的堆映射进进程。fanctl 自身的分配是那 1.2 MB，即几 KB
的配置加上一份传感器快照。运行 7 小时后做 30 秒探测，RSS 没有增长。

## 与同主板的 Go 守护进程对比

[coolercontrol][cc] 一类项目面对的是另一个问题，它们直接读写 hwmon。最接近的实现是
[`sonmihpc/AutoFan`][af]，专为这一系列主板编写：Go、显卡温度、`ipmitool raw` 写入。

| | AutoFan（Go） | fanctl |
| --- | --- | --- |
| 温度来源 | 仅 NVML，进程内 | IPMI raw 批量 + NVML |
| 通过 IPMI 读取的传感器 | 无 | 4–7 个，批量 |
| CPU / 机箱温度 | 不读 | 读 |
| 每次采样启动的进程 | 0 | 1（`exec`） |
| 每次占空比变化启动的进程 | 每个引脚一个，goroutine 并发 | 1（`exec`） |
| NVML 初始化 | 每次采样都 `nvml.Init()` + `Shutdown()` | 一次，延迟初始化 |
| 迟滞 / 防抖 | 无 | 按分区非对称 |
| 分区 / 一个引脚多个输入 | 无 | 有 |
| 读数失败时 | 从设备列表移除；若列表清空则温度取 0，落到最低档 | 先保持，宽限后按分区降档 |
| SIGTERM 复位 | 无 | 每个被驱动引脚写回待机值 |
| 配置 | YAML，`mode: max\|mean`，阈值表 | TOML，分区、联动、分区级边界 |

AutoFan 不使用 `ipmitool sdr`，它在进程内调用 NVML，读取不消耗进程，因此每次采样比 fanctl
的 183 ms 更便宜，这对只观察显卡的程序是合适的设计。它也无法读取 CPU 与机箱空气温度，
曲线按显卡组而非分区组织，并且每个周期都重新初始化驱动库。fanctl 每周期启动一个
`ipmitool` 进程，是因为它需要 BMC 提供 NVML 无法给出的 CPU、供电与进风温度；进程一旦
存在，每增加一个传感器的开销是 13–17 ms。

写入方面 fanctl 每次变化约快 3 倍，原因是它每周期启动一个 `ipmitool`，而不是每个引脚一个。

[af]: https://github.com/sonmihpc/AutoFan
[cc]: https://gitlab.com/coolercontrol/coolercontrol

## 降低开销

1. **加大 `interval_seconds`。** 10 秒是为响应速度选的，不是为开销；冷却液以升计的机器
   用 30 秒足够。
2. **少引用传感器。** 只有分区引用的传感器才会被读取；在 `platform.toml` 里声明二十个
   没有代价，每周期全读一遍每个要 13–17 ms。
3. **在没有 NVIDIA 显卡的机器上去掉 GPU 特性**：二进制小 106 KB，常驻内存少 20 MB。
4. **不需要日志中的转速时去掉转速计**：七个读数变四个，183 ms 变 130 ms。

解析每周期 560 ns，进程启动占据其余绝大部分耗时，因此没有其他值得优化的地方。
