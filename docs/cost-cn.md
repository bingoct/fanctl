# 开销

[English](cost.md) · **简体中文**

控制一把风扇要花多少，在这台 TYAN S8030GM2NE（AST2500，ipmitool 1.8.19，Debian 13）
上于 2026-10-25 实测。下面每个数字都来自那台机器，不是来自数据手册；产生这些数字的
脚本在开发仓库的 `.workbuddy/scripts/` 里。

相关：[设计](design-cn.md) · [配置](config-cn.md) · [平台](platform-cn.md)

## 一个周期的全部开销

| 步骤 | 耗时 | 说明 |
|---|---|---|
| 读分区用到的全部传感器（4 个温度 + 3 个转速） | 183 ms | 一次 `ipmitool exec` |
| 显卡，进程内首次调用 | 31 ms | `dlopen` NVIDIA 库 |
| 显卡，之后每次 | < 1 ms | 每张卡 5 µs |
| 聚合、曲线、合并 | 微秒级 | 几个数之间的纯算术 |
| 写变化的引脚（4 个） | 135 ms | 一次 `ipmitool exec`，只在有变化时 |
| **稳态合计** | **每 10 秒约 185 ms** | 单核 1.8 %，常驻 28 MB |

运行 7 小时 36 分后累计 CPU 时间：**5.5 秒** —— 单核 0.02 %。空载时进程在周期之间
睡眠，一个字都不写。

## 读取

`ipmitool sdr` 会走完整张 Sensor Data Repository，每一行做一次 Get Sensor Reading：
53 行、53 次往返、**2.9 秒**，而且每轮都这样，跟你想要几个值无关。

| 方法 | 1 个读数 | 4 个 | 7 个 |
|---|---|---|---|
| `ipmitool sdr`（整表 53 行） | 2 925 ms | 2 925 ms | 2 925 ms |
| `ipmitool sdr get <名字>`，每个名字一个进程 | 156 ms | — | — |
| **`ipmitool exec` + raw**（fanctl 的做法） | **88 ms** | **130 ms** | **183 ms** |

各取五轮最快值，测量时控制循环处于停止状态，没有别的进程在跟 BMC 说话。这张表能
读出两件事：

**成本的单位是进程，不是传感器。** `ipmitool` 启动、打开 `/dev/ipmi0`、建立接口要
~75 ms；同一个进程里每多一条 `raw 0x04 0x2d` 只要 13–17 ms。批处理读七个值，比开
两个进程各读一个还便宜。

**`sdr get` 也不省**，因为它是每个名字一个进程**外加**一次仓库遍历：同一次测量里
一个传感器 156 ms，三个 2.6 秒；而且某个 BMC 答得慢的传感器会把同一次调用里所有的
名字一起拖住。这就是 daemon 热路径上从不使用它的原因 —— `check` 用它，只用一次，
用来核对编号。

`exec` 的技巧本身很简单：`ipmitool` 可以从 stdin 读命令列表。

```text
raw 0x06 0x01                                   # 分隔符，15 字节
raw 0x04 0x2d 0x01                              # CPU_Tctl
raw 0x06 0x01
raw 0x04 0x2d 0x60                              # CPU_FAN 转速
```

每条命令前插入分隔符，意味着失败的命令留下一个**空洞**，而不是把后面的读数错位到
别的名字上 —— 见[设计](design-cn.md#读取)。分隔符本身的开销测不出来：七个读数带
分隔符（183 ms）和四个不带（130 ms）算下来是同一个每读数斜率。

## 写入

同一套机制，同一个收益：

| 方法 | 4 个引脚 |
|---|---|
| 每个引脚一个 `ipmitool raw`，四个进程 | 419 ms |
| **一次 `ipmitool exec`** | **135 ms** |

各测一次；同一台机器更早的测量是 356 ms 和 125 ms。BMC 的延迟本身就会漂几十毫秒，
所以请把它们当成"大约快 3 倍"，而不是精确值。

写路径**只写确认值发生了变化的引脚**，所以温度稳定的机器一个写命令都不发：10 分钟
正式控制只在第一轮发了四条写命令，之后没有。

每条命令是否成功，由 BMC 的应答（`fd 19 00`，三个字节）逐个判定，而不是看 `ipmitool`
的退出码 —— `exec` 遇到失败会继续跑后面的命令，但整体仍然退出 1，所以退出码说不出
**是哪个**引脚失败。槽位协议免费给出了这个答案。

## 二进制体积

1 505 240 字节（1.44 MiB），已 strip，`lto = "thin"`、`codegen-units = 1`、
`panic = "abort"`。除 libc 和 libgcc_s 外静态链接。

| 分区 | 字节 | 占文件 |
|---|---|---|
| `.text`（代码） | 1 200 550 | **79.8 %** |
| `.rodata`（常量、字符串、表） | 90 638 | 6.0 % |
| `.eh_frame` + `.eh_frame_hdr`（栈展开表） | 99 344 | 6.6 % |
| `.rela.dyn`（动态重定位） | 57 456 | 3.8 % |
| `.gcc_except_table` | 5 860 | 0.4 % |
| 文件头、节头、对齐 | ~51 000 | ~3.4 % |

### 代码从哪来

把每个 `.text` 符号按定义它的 crate 归类（demangle 后共归到 1 194 326 字节）：

| Crate | 占代码 | 是什么 |
|---|---|---|
| `fanctl` | **17.9 %** | 本程序，约 5 100 行 |
| `clap_builder` | 17.9 % | 命令行解析 |
| `core` | 14.5 % | `Option`、迭代器、格式化 |
| `std` | 9.9 % | 标准库 |
| `toml_edit` | 8.3 % | TOML 解析（经 `toml`） |
| `alloc` | 6.9 % | 内存分配 |
| `gimli`、`addr2line`、`rustc_demangle` | 5.7 % | panic backtrace 的符号化 |
| `nvml_wrapper_sys` | 4.6 % | NVIDIA 驱动绑定 |
| 无法归因（泛型实例） | 3.5 % | 符号名里没有 crate 的胶水 |
| `winnow` | 2.1 % | 解析器组合子，在 `toml` 下面 |
| `tracing_subscriber` | 1.9 % | 日志管道 |
| `hashbrown` | 1.5 % | `HashMap` |
| 约 20 个更小的 crate | 5.3 % | `signal-hook`、`miniz_oxide`、`strsim`…… |

由此有三点结论，其中两点正是 release profile 长成现在这样的原因。

**命令行解析和整个守护进程一样贵。** 两个子命令、四个参数，`clap` 占了 18 % 的代码。
彩色输出已经关掉（`default-features = false`），省了 81 KB；剩下的是 derive 机制
和帮助信息渲染器。手写 `argv` 的 `match` 能省掉大部分，代价是没人写过的 `--help`。

**`panic = "abort"` 是值得的。** 即使开着 abort，栈展开表仍占文件的 6.6 %（`std` 里的
`catch_unwind` 需要它们），但从 `unwind` 改成 `abort` 在这个代码库上实测 **−29 %**，
因为它去掉了每一条清理路径和大部分 `.eh_frame`。代价是 panic 时没有符号化调用栈；
需要时用 `--config 'profile.release.panic="unwind"'` 重编。

**TOML + 解析器组合子约 10 %。** 配置每个进程只读一次，这是为方便付的钱。手写解析器
会更小，也更差。

可选 feature 是可测量的：`--no-default-features`（无 NVML，也就没有显卡温度）编译出
**1 399 248 字节**，小 106 KB —— 文件的 7 %。

## 运行期占用

| 构建 | RSS | 其中匿名 | 线程 |
|---|---|---|---|
| 默认（含 NVML） | 28 MB | 21 MB | 2 |
| `--no-default-features` | 8 MB | 1.2 MB | 1 |

这个差值不是 fanctl 的：链接 NVIDIA 驱动会把驱动自己的堆映射进进程。fanctl 自己的
分配是那 1.2 MB —— 几 KB 配置加一份传感器快照，而且不增长：运行 7 小时后做 30 秒
探测，RSS 一动不动。

## 与同一块板上的 Go 守护进程对比

[coolercontrol][cc] 之类的项目解决的是另一个问题（它们走 hwmon）。最接近的同类是
[`sonmihpc/AutoFan`][af]，恰好就是为这块主板写的：Go、显卡温度、`ipmitool raw` 写入。
它的源码小到可以整个读完，所以能做一次诚实的对比。

| | AutoFan（Go） | fanctl |
|---|---|---|
| 温度来源 | 只有 NVML，进程内 | IPMI raw 批处理 + NVML |
| 经 IPMI 读的传感器 | **无** | 4–7 个，批处理 |
| CPU / 机箱空气温度 | 不读 | 读 |
| 每次采样的进程数 | 0 | 1（`exec`） |
| 每次改档的进程数 | **每个引脚一个**，并发 goroutine | 1（`exec`） |
| NVML 初始化 | 每个采样都 `Init()` + `Shutdown()` | 惰性初始化一次 |
| 防抖 | 无 | 每分区非对称 |
| 分区 / 一个引脚多个源 | 无 | 有 |
| 读取失败时的行为 | 该卡从列表里去掉；列表空了就返回温度 0 → 落到最低档 | 保持，宽限期后进本分区兜底 |
| SIGTERM 复位 | 无 | 每个被驱动引脚回到待机档 |
| 配置 | YAML，`mode: max\|mean`，阈值表 | TOML，分区、联动、每分区上下限 |

那个 Go 项目**没有**使用 `ipmitool sdr` —— 它在进程内调 NVML，所以读取上一个进程都
不花。这比 fanctl 的 183 ms 便宜，而且对一个只看显卡的程序来说，这是正确的设计。

它同时也看不到 CPU 和机箱空气，只有一套按显卡集的曲线而不是按分区，并且每个间隔都
重新初始化一次驱动库。fanctl 每周期花一个 `ipmitool` 进程，是因为它反正要用 BMC ——
为了 CPU、VRM 和空气这些 NVML 一无所知的传感器 —— 而进程一旦存在，把所有传感器塞
进去每个只要 13–17 ms。

写入上 fanctl 大约快 3 倍，不是因为 Go 慢，而是因为它每个引脚起一个 `ipmitool`
而不是每轮一个。

[af]: https://github.com/sonmihpc/AutoFan
[cc]: https://gitlab.com/coolercontrol/coolercontrol

## 想更省的话

按实际效果排序：

1. **调大 `interval_seconds`。** 10 秒是为响应速度选的，不是为开销；热容以升计的
   机器 30 秒完全够。
2. **少引用几个传感器。** 只有分区点名的传感器才会被读 —— 在 `platform.toml` 里声明
   二十个不花任何代价，每周期读它们才花 13–17 ms/个。
3. **在没有 N 卡的机器上关掉 gpu feature**：106 KB 二进制和 20 MB 常驻内存。
4. **不要转速就把 `[tachometers]` 去掉**：七个读数变四个，183 ms 变 130 ms。

其余都不值得优化。解析器已经是每轮 560 ns，分配次数是几十，剩下的开销全在进程启动。
