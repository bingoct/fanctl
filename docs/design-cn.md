# 设计

[English](design.md) · **简体中文**

这个守护进程为什么是这样。文中提到的配置项见 [配置](config-cn.md)，
每一步的实测开销见 [开销](cost-cn.md)。

## 一个周期

单线程，一个循环，没有 async 运行时：

```text
   ┌──────────────────────────────────────────────────────────────┐
   │ 1  采集   分区引用到的每个传感器，一次 ipmitool exec：        │
   │           BMC 出温度，NVML 出显卡温度                         │
   ├──────────────────────────────────────────────────────────────┤
   │ 2  聚合   每个分区：对本周期真正有读数的源取 max 或 mean      │
   ├──────────────────────────────────────────────────────────────┤
   │ 3  曲线   每个分区：温度 → 占空比，且只在下降方向防抖         │
   ├──────────────────────────────────────────────────────────────┤
   │ 4  合并   同一引脚被多个分区认领 → 取最大；再跑 [[follows]]； │
   │           最后夹到 [min, max]                                 │
   ├──────────────────────────────────────────────────────────────┤
   │ 5  下发   只写值变了的引脚，一次 ipmitool exec，               │
   │           靠 BMC 的应答逐引脚确认                             │
   └──────────────────────────────────────────────────────────────┘
                        睡到下一个周期
```

第 2 到 5 步都是对自有数据做运算的纯函数。这是刻意的：整套控制逻辑可以脱离 BMC、
GPU、主板测试,也确实是这样测的（`tests/control_logic.rs`，加上各模块内的单元测试）。

周期**含**本轮耗时。10 秒周期里读用掉 130 ms，就只睡 9.87 秒，不是再额外睡 10 秒。
如果某一轮真的超了周期，日志里会写 "cycle overran the interval"，下一轮立刻开始，
而不是让节奏一路后移。

不重读配置，也不自己转后台。`systemd` 负责前台运行和重启；改配置就是重启进程，
这样一份半有效的文件永远没有机会接管一台正在运行的机器。

## 读取

BMC 是瓶颈，而最顺手的那个调用恰好是错的：`ipmitool sdr` 会走完整张 Sensor Data
Repository，一行一次往返 —— 在这块板子上 2.9 秒。fanctl 改成只问分区引用到的那些
传感器，用 `raw 0x04 0x2d <传感器编号>`，并且把整串命令通过 stdin 喂给**一个**
`ipmitool exec` 进程。

`exec` 碰到失败的命令不会停下：它跳过那条的输出继续跑。如果按行对应读数，一个坏
传感器就会把它后面所有读数整体前移，错位到别的名字上 —— 得到一条看起来很合理、
却在控制错误对象的曲线。所以每条读命令前面都插一条输出长度固定的分隔命令
（`raw 0x06 0x01`），应答按**槽位**切：

```text
raw 0x06 0x01            <- 15 字节：槽位开始
raw 0x04 0x2d 0x01       <- CPU_Tctl 的读数
raw 0x06 0x01            <- 下一个槽位
raw 0x04 0x2d 0x20       <- 没有输出：这个传感器失败了
raw 0x06 0x01
raw 0x04 0x2d 0x31       <- 有读数，仍然对应正确的传感器
```

空洞的含义是"这条失败了"，不是"后面全部左移"。同一套协议也服务写路径，那里空洞
的含义是"这个引脚没有收到确认"（见 [开销](cost-cn.md#写入)）。

raw 应答不是 SDR 读数：第一个字节是原始值，而它是温度还是转速计数取决于传感器。
fanctl 不套用 SDR 记录里的 M/B 系数，这一点只有靠 `check` 在真实主板上验证假设才
成立（原始值 × 系数必须与 `ipmitool sdr` 相差 2 ℃ 以内，否则拒绝通过）。标记为
"no reading"、`ns`、`disabled` 的读数一律当作**缺失**，绝不当作 0 ℃ —— 缺数据的
传感器不能看起来像一台凉机器。

## 聚合

每个分区每周期把它的源归约成一个温度。

- `max`（默认）是安全的选择：分区保护它能看到的最高温，所以一张烫卡不会被三张凉卡
  平均掉。
- `mean` 用于那种确实服务一堆东西的分区 —— 一排硬盘、一组吸混合风的冷排扇。

只有**本周期真有读数**的源参与计算。一个活的加一个死的做 `mean`，结果是那个活的值，
不是它的一半。一个分区一个活源都没有，就是[失败策略](#读数消失之后)要处理的情况。

`GPU` 不是传感器，是关键字：NVML 能看到的所有 N 卡里最高的那张。`GPU1` 是某一张卡。
两个分区，两种视角：

```toml
# 冷排只给这两张卡散热
[[zones]]
name = "radiator"
monitor_sources = ["GPU1", "GPU2"]

# 前面板给整个机箱供风，包括自扇卡
[[zones]]
name = "intake"
monitor_sources = ["CPU_Tctl", "GPU"]
```

这个区别重要，是因为自带风扇的卡会把热量排进机箱，却不由冷排散掉。让冷排跟 `GPU`
走，那张卡就会白白拉起冷排；让前面板只跟 `GPU1`/`GPU2` 走，它就得不到冷空气。
一个"GPU 温度"设置项无法表达这两种需求，这就是分区的由来。

## 曲线

分区的 `thresholds` 是阶梯：温度达到 `temperature` 就用 `duty_cycle`，直到下一档。
超过最高档时保持最高档的占空比；低于第一档时停在 `default_duty_cycle`。

曲线是非对称的。升温和降温是两件不同的事：

| 方向 | 条件 | 动作 |
|---|---|---|
| 升 | `温度 >= 该档阈值` | **立即**切档，可以一次跳多档 |
| 降 | `温度 <= 当前档阈值 - debounce_celsius` | 降一档 |
| 跌破第一档 | `温度 <= 第一档阈值 - debounce_celsius` | 回 `default_duty_cycle` |
| 都不满足 | — | 不动 |

升温是安全事件，要立刻反应；降温是舒适事件，得自证清白。档位 55/70/85 → 40/60/100 %，
`debounce_celsius = 2`：70 ℃ 立刻上 60 %，但要降到 68 ℃ 才回 40 %；中间抖到 71 ℃
会立刻弹回 60 %，不用等。

这比滑动平均买到的东西更多：滤波器把**上升沿**也一起延迟了，而那恰好是显卡刚开始
干活时最不该延迟的方向。代价还小 —— 状态是一个整数，不是一个历史缓冲区。

`debounce_celsius` 必须小于相邻档位的间隔，否则某一档永远出不去，校验器会直接拒绝。

调曲线之前有一件物理事实值得知道：**低于风扇自身的最低转速，再低的占空比没有任何
效果。** 在 S8030 上，25 %、28 %、30 % 对原厂扇都是 828 RPM。写在那个地板以下的档位
不是配置错误，而是一把没法再慢的扇子 —— 唯一的解法是换扇或改 BMC 自己的策略，
不是在文件里写一个更小的数字。

## 合并

分区是各写各的，所以会撞车。解决顺序是固定的：

1. **同一引脚，多个分区 → 取最大值。** 取最大是唯一安全的规则：任何其他选择都会让
   文件里恰好排在后面的分区，把前面分区已经要求的散热降下来。
2. **`[[follows]]` 求不动点。** `pin = A, min_of = B` 意为 `A = max(A, B)`。规则反复
   施加直到不再变化，所以结果与书写顺序无关。规则成环（`A` 跟 `B`、`B` 跟 `A`）、
   自引用、或者某一端没有任何分区驱动，都会在加载期被拒。
3. **夹到 `[min_duty_cycle, max_duty_cycle]`** —— 放在最后，这样一个分区或一条联动
   规则都逃不出全局上下限。
4. **只写变化的引脚**，与上一次**确认成功**的值比较，所以 BMC 不会每 10 秒被重刷一遍
   它已经有了的数字。

联动之所以存在，是因为有些关系不是"一个分区"，而是分区之间的约束。"前面板不得比
冷排慢"不是一条曲线，把它写成同一引脚上的第二条曲线，只会和第一条打架。

## 读数消失之后

三种不同的失败，三种不同的回答。

**分区这一周期丢了读数。** 保持上一次的占空比。闪一下的传感器不该产生一次听得见的
档位跳变。连续 `fallback_after_cycles` 次（默认 2，10 秒周期即 20 秒）都读不到，分区
才放弃，降到自己的 `fallback_duty_cycle`，并在日志里说明。宽限之所以存在，是因为在
繁忙的 BMC 上，偶发一次 `ipmitool exec` 失败是正常事件。

**什么都读不到。** 跳过宽限，直接进兜底值。这不是抖动，是 BMC 或工具没了；为一个
谁也看不见的负载保持旧值，比一个已知安全的档位更糟。

**写入没有确认。** 该引脚在"已下发值"表里保持旧值，下个周期重试。失败的写永远不会
被记成成功 —— 那才是会让风扇停在待机档、日志却一直宣称成功的失败模式。

两条规则让兜底值得信任：

- `fallback_duty_cycle ≥ default_duty_cycle`，**逐分区**强制。读不到永远不能是这台
  机器能达到的最安静状态。
- 分区可以覆盖这两个值，水泵就是这么表达的：
  `default_duty_cycle = fallback_duty_cycle = 100`。读不到、空载、正在退出、传感器
  死了 —— 都无所谓，泵一直转。

### 退出

收到 `SIGINT` 或 `SIGTERM` 时，每个**被分区驱动**的引脚写回其分区的
`default_duty_cycle`（整批一次），然后退出 0。BMC 会保留它最后收到的值，所以不做
这一步的退出，机器就会停在上一次负载要求的转速上 —— 通常是它这辈子最吵的时候。

没有任何分区驱动的引脚，进去和出来都不碰。一个没人写过的引脚，fanctl 没有资格去
覆盖它；如果你为了看转速保留了一个通道声明，`check` 会提示一次，仅此而已。

## 日志行的用途

每周期一行：

```text
cycle temps CPU_Tctl=23.0 GPU0=28.0 GPU1=26.0 | fan CPU_FAN=690 SYS_FAN_1=966 | duty cpu=30 intake=35
```

三张表，全程 `key=value`，每段用一个裸词开头，切开不用猜。名字是排过序的，因为读数
存在 HashMap 里，顺序不稳会让两个完全相同的周期看起来不一样。

这一行刻意同时可读又可解析：它既是温度曲线的数据源，也是"循环还在转"的唯一常规证据。
这两件事是有冲突的 —— 每周期都打，空载机器一天 8 600 行 —— 所以按**变化**限流：

| 事件 | 级别 |
|---|---|
| 任一温度变化 ≥ 3 ℃ | INFO |
| 任一转速变化超过一个转速计计数 | INFO |
| 传感器或转速计出现/消失 | INFO |
| 什么都没变，距上次 INFO 不到 5 分钟 | DEBUG |
| 什么都没变，满 5 分钟 | INFO |
| 被驱动的风扇从转变成不转 | WARN |

两个阈值都是推导出来的，不是拍的。BMC 只报整数，空载 EPYC 整天在 22–24 ℃ 之间漂，
所以 2 ℃ 的判据在什么都没跑的时候仍然每分钟三条；3 ℃ 在抖动之上，而真实负载一两个
周期就会越过它。转速则被转速计本身量化 —— 100 % 的水泵永远在 5934 和 6072 之间来回，
正好是 138 RPM 的一个计数 —— 所以一个计数是噪声，两个计数才是运动。

转速参与这个判断，即使没有任何占空比是从它算出来的，因为这一对东西并不等价：占空比
是**要求**风扇头做什么，转速是风扇**实际**做了什么。风扇卡死、线松了、头子掉了供电，
在占空比里完全看不见，在转速里一眼就看出来。也正因如此，转速归零会单独打一条 WARN，
只在跳变的那一次打 —— 重复的告警就是会被忽略的告警。

## 安全与边界

软件检查什么，以及它检查不了什么：

- **先 `check` 再 `run`。** 它校验两份文件、按名字对着活 BMC 验证每个传感器编号、
  把一次 raw 读数和 `ipmitool sdr` 交叉核对（2 ℃ 容差）、列出显卡、做一次批量读。
  它绝不写任何 PWM 值。
- **先 `--dry-run` 再正式跑。** 跑完整控制循环，把本来会写的值打进日志，什么都不发。
- **通道 id 只做了语法校验。** 只有真的写一次才能证明 `0x00` 就是 CPU_FAN；`check`
  只能按名字猜，猜不到会给 warn 而不是报错。第一次正式运行，值得有人盯着
  `journalctl -u fanctl -f`，并且听着。
- **占空比 0 被拒绝。** `min_duty_cycle ≥ 1` —— 停转不是这个程序能表达的状态。
- **守护进程内部没有看门狗。** 进程死了，BMC 保留最后写入的值；重启归 systemd 管。
  如果守护进程停了很久，风扇会停在最后的档位（干净退出的话是待机档），而不是满转。
- **BMC 会把风扇拿回去。** 重启、断电、或者在 BMC 里切回 Smart Fan，都会丢掉 raw
  写入。daemon 下一轮会纠正，但刚重启的机器有几秒钟在厂商风扇策略下。

## 刻意不做的事

- **不做热重载。** 重启很便宜而且是原子的；半套生效的配置不是。
- **状态不落盘。** 启动时从当前温度重新定档。升温方向无防抖，所以重启不会导致过热，
  最多在日志里多一个档位。
- **不写 pid 文件、不自己转后台、不写日志文件。** systemd 和 journald 已经在做这些，
  做两遍正是守护进程和它的 unit 文件对不上的原因。
- **不加平均滤波。** 非对称曲线用另一种方式满足了同一个需求，而且没有延迟上升沿。
