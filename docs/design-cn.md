# 设计

[English](design.md) · **简体中文**

一个控制周期的处理流程。配置字段见 [config-cn.md](config-cn.md)，实测耗时见
[cost-cn.md](cost-cn.md)。

## 周期

单线程循环，无异步运行时：

```text
   ┌──────────────────────────────────────────────────────────────┐
   │ 1  读取   分区引用到的全部传感器，合并为一次 ipmitool exec   │
   │           温度来自 BMC，显卡温度来自 NVML                    │
   ├──────────────────────────────────────────────────────────────┤
   │ 2  聚合   每个分区归约为一个温度，取本轮有效读数的最大值或均值│
   ├──────────────────────────────────────────────────────────────┤
   │ 3  曲线   每个分区由温度查表得到占空比，仅下降方向带迟滞      │
   ├──────────────────────────────────────────────────────────────┤
   │ 4  合并   同一引脚被多个分区引用时取最大值；再应用 [[follows]]│
   │           最后按 [min, max] 截断                             │
   ├──────────────────────────────────────────────────────────────┤
   │ 5  写入   仅写变化的引脚，合并为一次 ipmitool exec，          │
   │           由 BMC 应答逐个确认                                │
   └──────────────────────────────────────────────────────────────┘
                        休眠至下一个周期
```

第 2 至第 5 步都是对自有数据的纯函数，因此控制逻辑不需要 BMC、显卡或主板即可测试：
`tests/control_logic.rs` 以及各模块内的单元测试。

周期包含本轮工作耗时。10 秒周期、读取耗时 130 ms，则休眠 9.87 秒。某轮超出周期时
记录日志，下一轮立即开始，不累积偏移。

配置只在启动时读取一次。修改配置等于重启，因此半合法的配置文件不会替换正在运行的配置。

## 读取

`ipmitool sdr` 遍历整张传感器表，每行一次往返，在 S8030 上耗时 2.9 秒。fanctl 只请求
分区引用到的传感器，命令形如 `raw 0x04 0x2d <传感器编号>`，全部命令通过 stdin 送入
同一个 `ipmitool exec`。

`exec` 遇到失败命令不会停止，而是跳过其输出继续执行。若按行匹配应答，一个失败的传感器
会让后续所有读数错位到别的名字上。因此每条读取之前插入一条输出长度固定的分隔命令
（`raw 0x06 0x01`），应答按槽位切分：

```text
raw 0x06 0x01            <- 15 字节，槽位开始
raw 0x04 0x2d 0x01       <- CPU_Tctl 的读数
raw 0x06 0x01            <- 下一个槽位
raw 0x04 0x2d 0x20       <- 无输出，该传感器失败
raw 0x06 0x01
raw 0x04 0x2d 0x31       <- 读数，仍在正确的传感器上
```

空槽位表示该条命令失败。写入路径使用同一协议，空槽位表示该引脚未被确认，见
[开销](cost-cn.md#写入)。

raw 应答不是 SDR 读数。第一个字节是原始值，该值是温度还是转速计数取决于传感器。
fanctl 不套用 SDR 记录中的 M/B 系数，这一假设由 `check` 在本板实测验证：原始值乘系数
必须与 `ipmitool sdr` 的结果相差不超过 2 ℃，否则 `check` 失败。应答标记为
"no reading"、`ns` 或 `disabled` 时按缺失处理，不当作 0 ℃。

## 聚合

每个分区每周期把所有输入归约为一个温度。

- `max`（默认）：分区保护它能看到的最高温度，单张高温显卡不会被其余低温显卡摊薄。
- `mean`：输入共享同一股气流时使用，例如冷排或一组硬盘。

只统计本轮有效上报的输入。对一个存活和一个失效的传感器取均值，结果等于存活者的温度。
分区完全没有有效输入时，按[失败策略](#读数缺失时的行为)处理。

`GPU` 是关键字而不是传感器，表示 NVML 能看到的所有显卡中的最高温度。`GPU1` 表示
按 NVML 序号指定的单张显卡。两个分区可以观察同一批硬件的不同子集：

```toml
# 冷排只覆盖这两张显卡。
[[zones]]
name = "radiator"
monitor_sources = ["GPU1", "GPU2"]

# 前面板为整个机箱供风，包括自带风扇的显卡。
[[zones]]
name = "intake"
monitor_sources = ["CPU_Tctl", "GPU"]
```

自带风扇的显卡把热量排到机箱里，这股热量不经过冷排。冷排分区若引用 `GPU`，会为并不经过
冷排的热量提速；前面板分区若只引用 `GPU1`/`GPU2`，机箱进风会不足。

## 曲线

分区的 `thresholds` 是阶梯：温度大于等于某一档的 `temperature` 时使用该档的
`duty_cycle`，直到下一档。高于最后一档时保持最后一档的占空比，低于第一档时使用
`default_duty_cycle`。

曲线的两个方向不对称：

| 方向 | 条件 | 动作 |
| --- | --- | --- |
| 上升 | `temperature >= 该档 temperature` | 立即切换，可跨多档 |
| 下降 | `temperature <= 当前档 temperature - debounce_celsius` | 降一档 |
| 低于第一档 | `temperature <= 第一档 temperature - debounce_celsius` | 回到 `default_duty_cycle` |
| 其他 | — | 保持 |

台阶为 55/70/85 → 40/60/100 %、`debounce_celsius = 2` 时，70 ℃ 给出 60 %，降到 68 ℃
才回到 40 %。读数短暂升到 71 ℃ 会立即回到 60 %，不等迟滞。

滑动平均同样会延迟上升沿，而上升沿是负载出现时必须及时响应的方向。迟滞状态是一个整数，
不需要历史缓冲区。

`debounce_celsius` 必须小于相邻两档的间隔，否则该档无法退出，校验器会拒绝这样的配置。

风扇的物理下限会影响曲线设计：低于某把风扇的最低转速后，再降低占空比不产生任何变化。
S8030 原装风扇在 25 %、28 %、30 % 下都是 828 RPM。写在这个下限以下的台阶不是配置错误，
而是风扇无法更慢。

## 合并

各分区独立求值，结果可能冲突。处理顺序固定：

1. **同一引脚被多个分区引用时取最大占空比。** 其他规则会让后求值的分区降低前一个分区
   已经要求的散热。
2. **`[[follows]]` 迭代到不动点。** `pin = A, min_of = B` 表示 `A = max(A, B)`。规则反复
   应用直到不再变化，因此结果与书写顺序无关。规则成环、自我引用、或某一端没有分区驱动，
   在加载期即报错。
3. **按 `[min_duty_cycle, max_duty_cycle]` 截断**，放在最后，分区与联动规则都无法越过
   全局边界。
4. **只写变化的值**，与上一次确认成功的值比较，避免每 10 秒重发同一个占空比。

`[[follows]]` 用于表达引脚之间不成曲线的约束，例如"前面板不得比冷排慢"。把它写成同一
引脚上的第二条曲线会与第一条冲突。

## 读数缺失时的行为

三种失效，三种处理。

**本轮分区没有读数。** 保持上一档占空比，偶发一个周期的缺失不产生可听见的转速变化。
连续 `fallback_after_cycles` 个周期（默认 2，10 秒周期下为 20 秒）缺失后，分区降到自己的
`fallback_duty_cycle` 并记录日志。繁忙的 BMC 上偶发一次 `ipmitool exec` 失败属正常现象，
宽限周期为此而设。

**所有传感器都读不到。** 跳过宽限，立即写入兜底值。此时依据的是无人能观察的负载，
保持旧值不如使用已知安全值。

**写入未被确认。** 该引脚在"上次下发"表中保留旧值，下个周期重发。未确认的写入不会
被记为成功。

两条规则保证兜底值可靠：

- 逐分区强制 `fallback_duty_cycle >= default_duty_cycle`，保证完全读不到数据时不会是
  整机最安静的状态。
- 分区可以覆盖这两个值。水泵使用 `default_duty_cycle = fallback_duty_cycle = 100`，
  空载、读不到数据、退出时都保持该占空比。

### 退出

收到 `SIGINT` 或 `SIGTERM` 后，所有被驱动的引脚按所属分区的 `default_duty_cycle` 一次性
写回，进程返回 0。BMC 会保持最后一次写入的值，没有这一步，机器会停在上一个负载要求的
转速上。

没有被任何分区驱动的引脚不写入，运行期间与退出时都不写。`check` 对这类引脚给出
`[warn]`，只为读取转速而声明的通道属于这种情况。

## 每周期日志

每周期输出一行：

```text
cycle temps CPU_Tctl=23.0 GPU0=28.0 GPU1=26.0 | fan CPU_FAN=690 SYS_FAN_1=966 | duty cpu=30 intake=35
```

三张表，统一 `key=value` 形式，每张表前有一个单独的词作为分隔。名字经过排序，因为读数
存放在哈希表中，顺序不稳会让两个相同的周期看起来不同。

这一行既可用于机器解析（画温度曲线的数据来源），也是控制循环仍在运行的例行证据。
若每周期都输出，空载机器一天约 8600 行，因此每五分钟输出一条，其余周期降到 DEBUG：

| 事件 | 级别 |
| --- | --- |
| 距上一条周期行满 5 分钟 | INFO |
| 不足 5 分钟，且没有别的话要说 | DEBUG |
| 占空比发生变化 | INFO，并把当时的温度带上 |
| 被驱动的风扇由转动变为零 | WARN |

级别只由这些事件决定。早先的做法是"任一温度变化 3 ℃ 也升到 INFO"，用来记录心跳之间的瞬态。
但空载机器上这个阈值正好压在 `CPU_Tctl` 的抖动上——它在 21 至 24 ℃ 之间来回跳，
某一天的 295 个间隔里有 189 个由温度触发，其中 113 个是这段抖动，真正的心跳只轮上 60 次。
温度变化只有在推动风扇时才值得记，而那种情况现在有自己的一行：

```text
duty cycle changed pin=SYS_FAN_2 from=30 to=35 temps=CPU_Tctl:26.0,GPU0:55.0,GPU1:26.0
```

原因随结果一起落地，五分钟的采样就不必再解释四分钟前发生的调整。

启动后每个引脚的第一次写入记为 `duty cycle initialised`，不带温度：它不是被什么触发的，
只是守护进程在自己从未见过前值的引脚上第一次落定曲线。

转速写在这一行里，但不参与级别判定。转速读数自身有一两个计数的抖动——水泵在 100 % 下
于 5934 与 6072 RPM 之间来回跳动，相差一个计数。温度没动而转速动了，不单独输出一行。
转速归零则要输出：占空比是下发的值，转速是风扇实际做出的结果，风扇堵转、线缆松动、供电
丢失只在转速上可见。这一条只在变化的那一刻输出，不每周期重复。

## 安全与边界

软件会检查：

- **先 `check`，后 `run`。** 校验两份配置，按名字核对每一个传感器编号，将一次 raw 读数
  与 `ipmitool sdr` 交叉验证（容差 2 ℃），列出显卡，做一次批量读取。不写入任何 PWM。
- **先 `--dry-run`，后正式运行。** 运行完整循环，日志中记录本应写入的值。
- **拒绝 0 占空比。** `min_duty_cycle >= 1`，停转服务器风扇不是本程序可以表达的状态。

软件无法保证：

- **通道号只做语法检查。** 只有实际写入某个通道才能确认它对应哪个风扇头。`check` 依据
  名字推测对应关系，无法推测时给出警告。
- **进程内没有看门狗。** 进程退出后 BMC 保持最后一次写入的值，重启由 systemd 负责。
  守护进程长时间停止时，风扇保持最后一次写入的占空比；正常退出则为待机值。
- **BMC 可以收回控制权。** 重启、断电或在 BMC 中切回 "Smart Fan" 会丢弃 raw 写入。
  守护进程在下一个周期重新写入，刚重启的机器会有几秒处于厂商策略之下。

## 非目标

- **不做热重载。** 重启代价低且原子；部分生效的配置无法保证一致。
- **不在磁盘上保存状态。** 启动时依据当前温度重新定档。升温方向无阻尼，重启不会导致
  过热，最多多出一条日志。
- **不写 pid 文件、不自守护化、不写日志文件。** 这些由 systemd 与 journald 负责。
- **不做滑动平均。** 非对称曲线在不延迟上升沿的前提下解决了同样的问题。
