# 设计

[English](design.md) · **简体中文**

一个控制周期做五件事。配置字段见 [config-cn.md](config-cn.md)，实测耗时见
[cost-cn.md](cost-cn.md)。

## 周期

单线程循环，无异步运行时：

```text
   ┌──────────────────────────────────────────────────────────────┐
   │ 1  读取   分区引用到的全部传感器，合并为一次 ipmitool exec   │
   │           温度来自 BMC，显卡温度来自 NVML                    │
   ├──────────────────────────────────────────────────────────────┤
   │ 2  聚合   每个分区归约为一个温度，取本轮有效读数的最大值或均值│
   ├──────────────────────────────────────────────────────────────┤
   │ 3  曲线   温度查表得到占空比，仅下降方向带迟滞                │
   ├──────────────────────────────────────────────────────────────┤
   │ 4  合并   同一引脚被多个分区引用时取最大值；再应用 [[follows]]│
   │           最后按 [min, max] 截断                             │
   ├──────────────────────────────────────────────────────────────┤
   │ 5  写入   仅写变化的引脚，合并为一次 ipmitool exec，          │
   │           由 BMC 应答逐个确认                                │
   └──────────────────────────────────────────────────────────────┘
                        休眠至下一个周期
```

第 2 至第 5 步是纯函数，不碰 BMC、显卡与主板，因此控制逻辑可以离线测试：
`tests/control_logic.rs` 加上各模块的单元测试。

周期包含本轮工作耗时：10 秒周期、读取 130 ms，休眠 9.87 秒。某轮超时则记录日志，
下一轮立即开始，不累积偏移。

配置只在启动时读取一次，修改配置等于重启；半合法的配置文件不会替换正在运行的配置。

## 读取

`ipmitool sdr` 遍历整张传感器表，每行一次往返，S8030 上耗时 2.9 秒。fanctl 只请求
分区引用的传感器（`raw 0x04 0x2d <编号>`），全部命令通过 stdin 送入同一个
`ipmitool exec`。

`exec` 遇到失败命令会跳过输出继续执行。若按行匹配应答，一个失败的传感器会让后面
所有读数错位到别的名字上。因此每条读取前插入一条输出长度固定的分隔命令
（`raw 0x06 0x01`），应答按槽位切分：

```text
raw 0x06 0x01            <- 15 字节，槽位开始
raw 0x04 0x2d 0x01       <- CPU_Tctl 的读数
raw 0x06 0x01            <- 下一个槽位
raw 0x04 0x2d 0x20       <- 无输出，该传感器失败
raw 0x06 0x01
raw 0x04 0x2d 0x31       <- 读数，仍在正确的传感器上
```

空槽位表示该条命令失败。写入路径用同一协议，空槽位表示该引脚未被确认，见
[开销](cost-cn.md#写入)。

raw 应答的第一个字节是原始值，它是温度还是转速计数取决于传感器。fanctl 不套用
SDR 记录的 M/B 系数；这一假设由 `check` 在本板实测验证：原始值乘系数与
`ipmitool sdr` 相差超过 2 ℃ 即失败。应答为 "no reading"、`ns` 或 `disabled` 时
按缺失处理，不当作 0 ℃。

## 聚合

每个分区每周期把全部输入归约为一个温度。

- `max`（默认）：分区保护最热的输入，单张高温显卡不会被其余低温显卡摊薄。
- `mean`：输入共享同一股气流时使用，例如冷排或一组硬盘。

只统计本轮有效上报的输入：一个存活、一个失效的传感器取均值，结果就是存活者的温度。
分区完全没有有效输入时，按[失败策略](#读数缺失时的行为)处理。

`GPU` 是关键字：NVML 可见的全部显卡中的最高温度。`GPU1` 是按 NVML 序号指定的单张卡。
两个分区可以观察同一批硬件的不同子集：

```toml
# 冷排只覆盖这两张显卡。
[[zones]]
name = "radiator"
monitor_sources = ["GPU1", "GPU2"]

# 前面板为整个机箱供风，包括自带风扇的显卡。
[[zones]]
name = "intake"
monitor_sources = ["CPU_Tctl", "GPU"]
```

自带风扇的显卡把热量排进机箱，这股热量不经过冷排。冷排分区引用 `GPU` 会为不经过
冷排的热量提速；前面板分区只引用 `GPU1`/`GPU2` 则机箱进风不足。

## 曲线

`thresholds` 是阶梯：温度达到某一档的 `temperature` 就用该档的 `duty_cycle`，
直到下一档。高于最后一档保持最后一档，低于第一档用 `default_duty_cycle`。

两个方向不对称：

| 方向 | 条件 | 动作 |
| --- | --- | --- |
| 上升 | `temperature >= 该档 temperature` | 立即切换，可跨多档 |
| 下降 | `temperature <= 当前档 temperature - debounce_celsius` | 降一档 |
| 低于第一档 | `temperature <= 第一档 temperature - debounce_celsius` | 回到 `default_duty_cycle` |
| 其他 | — | 保持 |

台阶 55/70/85 → 40/60/100 %、`debounce_celsius = 2`：70 ℃ 给 60 %，降到 68 ℃ 才
回到 40 %；中途升到 71 ℃ 立即回到 60 %，不等迟滞。

不用滑动平均：它同样延迟上升沿，而上升沿是负载出现时必须及时响应的方向。迟滞状态
是一个整数，不需要历史缓冲区。

`debounce_celsius` 必须小于相邻两档的间隔，否则该档无法退出；校验器拒绝这样的配置。

风扇的物理下限影响曲线设计：低于最低转速后，降低占空比没有效果。S8030 原装风扇
25 %、28 %、30 % 都是 828 RPM；写在下限以下的台阶不是配置错误，是风扇无法更慢。

## 合并

各分区独立求值，结果可能冲突。处理顺序固定：

1. **同一引脚取最大占空比。** 其他规则会让后求值的分区降低前一个分区要求的散热。
2. **`[[follows]]` 迭代到不动点。** `pin = A, min_of = B` 即 `A = max(A, B)`，反复
   应用直到不再变化，结果与书写顺序无关。规则成环、自引用、某端无分区驱动，加载期
   报错。
3. **按 `[min_duty_cycle, max_duty_cycle]` 截断**，放在最后，分区与联动规则都越不过
   全局边界。
4. **只写变化的值**，与上一次确认成功的值比较，不向 BMC 重发它已有的值。

`[[follows]]` 表达引脚之间不成曲线的约束，例如"前面板不得比冷排慢"。写成同一引脚的
第二条曲线会与第一条冲突。

## 读数缺失时的行为

三种失效，三种处理。

**分区本轮没有读数。** 保持上一档，偶发一次缺失不产生可听见的变速。连续
`fallback_after_cycles` 个周期（默认 2，10 秒周期下 20 秒）缺失后降到
`fallback_duty_cycle` 并记日志。繁忙的 BMC 上单次 `ipmitool exec` 失败属正常，
宽限周期为此而设。

**所有传感器都读不到。** 跳过宽限，立即写兜底值。负载无人可见时，保持旧值不如
已知安全值。

**写入未被确认。** 该引脚在"上次下发"表中保留旧值，下个周期重发。未确认的写入
不会记为成功。

两条规则保证兜底值可靠：

- 逐分区强制 `fallback_duty_cycle >= default_duty_cycle`：完全读不到数据时，
  不会是整机最安静的状态。
- 分区可以覆盖这两个值。水泵用 `default_duty_cycle = fallback_duty_cycle = 100`，
  空载、无读数、退出时都保持 100。

### 退出

收到 `SIGINT` / `SIGTERM` 后，全部被驱动引脚按所属分区的 `default_duty_cycle`
一次性写回，进程返回 0。BMC 保持最后一次写入的值；没有这一步，机器会停在
上一个负载要求的转速上。

没有分区驱动的引脚不写入，运行期与退出时都不写。`check` 对其给出 `[warn]`；
只为读转速而声明的通道属于这种情况。

## 每周期日志

每周期一行：

```text
cycle temps CPU_Tctl=23.0 GPU0=28.0 GPU1=26.0 | fan CPU_FAN=690 SYS_FAN_1=966 | duty cpu=30 intake=35
```

三组 `key=value`，每组前有一个分隔词。名字排序，因为读数存在哈希表里，顺序不稳
会让两个相同周期看起来不同。

这一行可被机器解析（画温度曲线的数据源），也是循环仍在运行的例行证据。每周期都发
一天约 8 600 行，因此每五分钟发一条 INFO，其余降到 DEBUG：

| 事件 | 级别 |
| --- | --- |
| 距上一条周期行满 5 分钟 | INFO |
| 不足 5 分钟，且没有别的事 | DEBUG |
| 占空比变化 | INFO，附上当时的温度 |
| 被驱动风扇由转动变为零 | WARN |

级别只由这些事件决定。早先的版本让"任一温度变化 3 ℃"也升 INFO，用来记录心跳之间
的瞬态。空载机器上这个阈值正好压在 `CPU_Tctl` 的抖动上（21 至 24 ℃ 之间来回跳）：
某一天 295 个间隔里 189 个由温度触发，其中 113 个是这段抖动，真正的心跳只出现
60 次。温度变化只有在推动风扇时才值得记录，那种情况有自己的一行：

```text
duty cycle changed pin=SYS_FAN_2 from=30 to=35 temps=CPU_Tctl:26.0,GPU0:55.0,GPU1:26.0
```

原因随结果一起落地，五分钟的采样不必再解释四分钟前的调整。

启动后每个引脚的第一次写入记为 `duty cycle initialised`，不带温度：它不是被触发
的，是守护进程在从未见过前值的引脚上第一次落定曲线。

转速在行里，但不参与级别判定。转速自身有一两个计数的抖动（水泵 100 % 下在 5934
与 6072 RPM 之间跳，相差一个计数）；温度没动而转速动了，不单独出行。转速归零要
出行：占空比是下发的请求，转速是风扇实际的结果，堵转、线缆松动、供电丢失只在
转速上可见。这一条只在变化那一刻输出，不每周期重复。

## 安全与边界

软件会检查：

- **先 `check` 后 `run`。** 校验两份配置，按名字核对每个传感器编号，一次 raw 读数
  与 `ipmitool sdr` 交叉验证（容差 2 ℃），列出显卡，做一次批量读取。不写 PWM。
- **先 `--dry-run` 后正式运行。** 跑完整循环，日志记录本应写入的值。
- **拒绝 0 占空比。** `min_duty_cycle >= 1`；停转服务器风扇不是本程序可表达的状态。

软件无法保证：

- **通道号只做语法检查。** 只有实际写入才能确认通道对应哪个风扇头。`check` 按名字
  推测，推测不出时警告。
- **进程内没有看门狗。** 进程退出后 BMC 保持最后写入的值，重启由 systemd 负责。
  守护进程长期停止时风扇保持最后占空比；正常退出则为待机值。
- **BMC 可以收回控制权。** 重启、断电、切回 "Smart Fan" 都会丢弃 raw 写入。
  守护进程下个周期补写，刚重启的机器有几秒在厂商策略之下。

## 非目标

- **不做热重载。** 重启代价低且原子；部分生效的配置两者都不是。
- **不在磁盘保存状态。** 启动时按当前温度重新定档。升温方向无阻尼，重启不会过热，
  最多多一条日志。
- **不写 pid 文件、不自守护化、不写日志文件。** systemd 与 journald 已提供。
- **不做滑动平均。** 非对称曲线在不延迟上升沿的前提下覆盖了同样的需求。
